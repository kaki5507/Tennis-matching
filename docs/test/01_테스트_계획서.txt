================================================================================
 01. 테스트 계획서
================================================================================

1. 목적
 - 배포(Vercel) 후 실제 사용자가 들어오기 전에, 핵심 기능이 의도대로 동작하고
   권한/보안 규칙이 우회되지 않는지 체계적으로 확인한다.
 - 이후 기능 추가 시 기존 기능이 깨지는지(회귀) 빠르게 알 수 있는 기반을 만든다.

2. 테스트 대상 범위
 2-1. 포함 (In Scope)
   (1) 회원: 가입(본인인증/임시가입/관리자 초대코드), 로그인, 프로필, 탈퇴
   (2) 매칭: 방 생성, 참가 신청, 수락/거절, 결제 확인, 마감, 경기 완료, 신청 취소
   (3) 평가: 상호 평가(NTRP, 매너), 허위 구력 자동 조정/정지
   (4) 대회: 개설, 신청(단식/복식), 대진표 생성/초기화, 결과 입력, 트로피
   (5) 소통: 채팅, 댓글, 알림(푸시 포함), 코트 빈자리 알림 구독
   (6) 관리자: 대시보드 통계, 회원 관리/정지, CSV 내보내기, 작업 기록, 점검 모드
   (7) 공개 기능: 인기 시간대 추천, 부천 코트 예약 링크, 방문 집계
   (8) 인프라: 크론(코트 빈자리 확인), 마이그레이션, 환경변수
 2-2. 제외 (Out of Scope)
   - Supabase/Vercel/PortOne/Firebase 등 외부 서비스 내부 동작 (연동 지점만 검증)
   - 부천시 예약 사이트 자체의 가용성 (링크 이동까지만 확인)
   - 대규모 부하(수천 동시접속) 시험 (1차 오픈 규모 기준 간이 점검만 수행)

3. 테스트 레벨별 전략
 +--------+--------------------------------+------------------+----------------+
 | 레벨   | 대상                           | 방식             | 권장 도구      |
 +--------+--------------------------------+------------------+----------------+
 | 단위   | lib/ 순수 함수 (DB 불필요)     | 자동화           | Vitest         |
 | 통합   | 서버 액션 + Prisma + DB        | 자동화(테스트DB) | Vitest         |
 | 시스템 | 브라우저 전체 흐름             | 수동 -> 자동화   | Playwright     |
 | 보안   | 토큰/권한/입력검증             | 통합 + 수동      | Vitest + 수동  |
 | 비기능 | 성능, 반응형, 호환성           | 수동 + 도구      | Lighthouse 등  |
 +--------+--------------------------------+------------------+----------------+
 - 테스트 피라미드 원칙: 단위(많이, 빠르게) > 통합(핵심 규칙) > E2E(핵심 흐름 몇 개)
 - 외부 의존(Supabase Auth, PortOne, Firebase, 카카오맵)은 통합 테스트에서
   모킹(mock)하고, E2E에서는 실제 개발용 프로젝트를 사용한다.

4. 테스트 환경
 - 로컬   : npm run dev, 개발용 Supabase 프로젝트 또는 로컬 Postgres
 - 테스트 DB: 운영 DB와 반드시 분리 (DATABASE_URL을 테스트 전용으로).
              운영 DB에 테스트 데이터를 만들지 않는다. 마이그레이션은 migrate deploy.
 - 스테이징: Vercel Preview 배포 (PR/브랜치마다 자동 생성)
 - 운영   : 배포 직후 "스모크 테스트"만 수행 (08번 배포 전/후 체크리스트)
 - 브라우저: Chrome 최신, Safari(iOS), Samsung Internet(Android), 모바일 우선
 - 환경변수 구분: ALLOW_UNVERIFIED_SIGNUP, PORTONE_API_SECRET, CRON_SECRET 조합에 따라
   가입 동작이 달라지므로 IT-AUTH 시나리오에서 조합별로 확인한다.

5. 자동화 도입 순서 (권장)
 단계 1) vitest 설치, "test": "vitest run" 스크립트 추가
         (@/ 경로 별칭은 vitest.config.ts의 resolve.alias로 설정)
 단계 2) 02번 문서의 UT 케이스 작성 (lib/bracket, tournamentRules, gender, trophies,
         portone, maintenance). 이 단계는 DB 없이 바로 가능하다.
 단계 3) 03번 문서의 IT 케이스 작성. 방식 두 가지 중 택1
         (a) 테스트 전용 Postgres + 실제 Prisma, Supabase auth.getUser만 모킹  <- 권장
         (b) prisma 클라이언트 전체 모킹 (빠르지만 SQL 오류를 못 잡음)
 단계 4) Playwright로 E2E 핵심 3개 자동화 (가입->방 생성, 참가->수락, 관리자 로그인)
 단계 5) GitHub Actions: PR마다 tsc, eslint, vitest 실행. 실패 시 머지 금지.

 테스트 가능하도록 필요한 작은 리팩터링(코드 수정 필요)
 - app/actions/admin.ts 안의 regionOf, kstDayStart 등 순수 헬퍼는 "use server" 파일이라
   async 함수만 export 가능 -> lib/kst.ts, lib/region.ts로 분리 후 테스트
 - lib/levelIntegrity.ts의 상수/판정 로직을 순수 함수로 분리하면 DB 없이 검증 가능

6. 진입 기준 (테스트 시작 조건)
 - 해당 기능 코드가 main 또는 PR 브랜치에 병합 가능한 상태
 - tsc / eslint 오류 0건 (기존 LayoutProps 타입 오류 1건은 알려진 예외)
 - 테스트 DB 마이그레이션 적용 완료

7. 종료 기준 (배포 승인 조건)
 - 우선순위 [상] 테스트 케이스 100% 실행, 통과율 100%
 - 우선순위 [중] 통과율 90% 이상, 미통과 항목은 결함으로 등록되고 우회 방법 존재
 - 결함 등급 치명/높음 미해결 0건
 - 보안 체크리스트 [필수] 항목 전부 통과
 - 배포 후 스모크 테스트 통과

8. 우선순위 / 결함 등급 정의
 우선순위: 상 = 돈/개인정보/권한/핵심 흐름, 중 = 일반 기능, 하 = 표시/문구
 결함 등급:
   치명 : 데이터 유출, 권한 우회, 서비스 전체 중단, 데이터 손상
   높음 : 핵심 기능 불가(가입/방 생성/참가), 잘못된 정지/차단
   보통 : 일부 기능 오동작, 우회 가능
   낮음 : 문구, 레이아웃, 사소한 표시 오류

9. 위험 분석 (Risk)
 +------------------------------------------+--------+----------------------------+
 | 위험                                     | 영향   | 대응                       |
 +------------------------------------------+--------+----------------------------+
 | 서버 액션 직접 호출로 권한 우회          | 치명   | SEC 문서 전 항목, 토큰검증 |
 | 본인인증 임시가입으로 정지 회피          | 높음   | 이메일 기반 식별, PG 계약  |
